# DCU-2026-07-26-10 — Update discovery selects a compatible release target

## Decision

GitHub-backed update discovery reads a bounded catalog of the twenty most
recent releases with conditional ETag validation, discards drafts and
prereleases, validates release and asset records independently as typed bounded
data, and evaluates compatible releases by SemVer 2.0 precedence rather than
response order. Transport bytes, release count, asset count, and material
string lengths are bounded before data reaches application policy. An
unrelated malformed/non-SemVer entry or incomplete GitHub `starter` asset is
ignored; it cannot hide an older valid target. Build metadata never changes
precedence, and distinct releases tied at the same precedence are rejected as
ambiguous instead of being selected by provider order.

A direct build has one compile-time platform and distribution channel. Its
eligible asset name is exact:

- `DevCoordinator-<SemVer>-android.apk`;
- `DevCoordinator-<SemVer>-macos.dmg`; or
- `DevCoordinator-<SemVer>-windows.msix`.

The asset must be fully uploaded, have a positive provider-reported size, and
use the exact canonical GitHub repository, tag, and filename in its HTTPS
download URL. Ad-hoc macOS and self-signed Windows smoke artifacts never match
these production names. Direct builds reject a configurable destination and
open that verified installer URL itself.

Google Play, Mac App Store, and Microsoft Store channels are separately
explicit and valid only on their matching platform. Each Store release requires
an exact, non-empty, repository-owned
`DevCoordinator-<version>-<platform>-<store>-<product-id>.release.json` marker
uploaded only after the version is visible for the same product identity in
that Store. Its destination must be the exact official listing identity: the
canonical Android package at
`play.google.com`, or the build-pinned Apple/Microsoft product ID at
`apps.apple.com`/`apps.microsoft.com`.

The client selects the highest compatible newer SemVer within the bounded
catalog. No compatible target means no automatic prompt; a manual check
explains that the repository has a newer release for another target. Catalog
caches are distinct from the former single-release cache, so an older ETag or
asset-free cache cannot cross the new contract.

This supersedes only the latest-release endpoint choice in
DCU-2026-07-25-04. Release notifications remain non-installing handoffs, and
each platform's signing, notarization, Store, upgrade, and rollback boundary
remains independent.

## Why

Material alternatives considered:

- Treating the repository's latest release as universal was rejected because
  the first stable release legitimately contains only Android and must not be
  offered to macOS or Windows.
- Filtering only the latest release was rejected because a newer
  Android-only release could hide an older release that is still a valid
  upgrade for an installed desktop version.
- Requiring synchronized Android, macOS, and Windows assets in every stable
  release was rejected because missing Apple or Windows publisher identities
  would unnecessarily block an independently safe Android update.
- Trusting a platform substring, arbitrary download host, release-body link,
  or manifest-supplied redirect was rejected because it could select a smoke
  artifact or move the update action outside the configured repository and
  distribution channel.
- Treating every stable GitHub release as a Store release was rejected because
  repository publication does not prove that Google, Apple, or Microsoft has
  made the same version available.
- Failing the complete catalog for one unrelated interrupted asset upload or
  non-version tag was rejected because GitHub can retain a `starter` asset and
  repositories may contain other releases; each candidate instead fails closed
  on its own target evidence.
- A new signed release-manifest format was not required for notification-only
  selection: GitHub supplies the authenticated repository metadata, while
  Android, Apple, and Windows binary identities remain the final installation
  trust boundary. A signed manifest can be added later without weakening the
  exact asset contract.

The selected bounded catalog preserves an independent release cadence while
making every prompt truthful for the installed target and keeping automatic
checks cheap, size-limited, and cacheable.

## Evidence and verification

The release-update package covers bounded catalog parsing, draft/prerelease
filtering, duplicate and malformed entries, ETags, old-cache separation, and
catalog scheduling. The application adapter covers Android-only latest
releases, an older compatible desktop release, no compatible release,
platform/channel mismatch, exact filename and URL ownership, Store
destinations, suppression, automatic silence, and manual explanation. Release
acceptance additionally checks the public catalog with the same installed
target policy.

The provider behavior and handoff shapes were checked against the current
primary documentation for [GitHub release asset
states](https://docs.github.com/en/rest/releases/assets),
[GitHub release limits](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases),
[Google Play listing links](https://developer.android.com/distribute/marketing-tools/linking-to-google-play),
[Apple application IDs](https://developer.apple.com/help/app-store-connect/reference/app-information/app-information),
and [Microsoft Store product
identity](https://learn.microsoft.com/en-us/windows/apps/publish/view-app-identity-details).
