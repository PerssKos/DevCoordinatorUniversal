# DCU-2026-07-26-07 — Production connection, updates, and capabilities are explicit

## Decision

The installed application's canonical production gateway is
`https://console.classified.guru/api/v2`. Android exposes one primary connect
action for that gateway, opens the system browser for OAuth, and returns
through the registered application callback. It does not ask for a hostname,
URL, coordinator bearer, or “local desktop” mode. Windows and off-host macOS
use the same remote flow. The legacy loopback preview remains a separately
labeled option only for the macOS app on the verified coordinator host.

The canonical public source and release-update repository is
`PerssKos/DevCoordinatorUniversal`. Distributable builds inject that exact
non-secret `owner/repository` slug through `UPDATE_REPOSITORY`; the update
client uses its latest stable GitHub Release and hands installation to the
platform channel. A local build without an injected source reports updates as
unconfigured rather than guessing a repository. Publication, signing, and
channel readiness remain separately evidenced release operations.

The client treats advertised native-v2 capabilities as the runtime truth.
Knowing how to parse a capability does not enable its UI. In particular,
`lifecycle.manage` stays hidden while the canonical coordinator lacks the
durable plan/fingerprint/apply contract for archive, permanent removal, and
restore. Port requests preserve the user's exact inclusive bounds. A lease
release control appears only when the server reports that exact lease as
releasable for the current device session; the client does not infer ownership
from agent names, labels, or local history.

## Why

Material alternatives considered:

- Retaining a generic Android host/URL/token form was rejected because the
  production service is fixed and OAuth supplies the user/device credential;
  the extra fields exposed privileged implementation details and invited
  invalid setup.
- Guessing a release repository from package identity or source remotes was
  rejected because local and CI checkouts can differ and could silently direct
  update prompts to the wrong publisher.
- Keeping updates attached to the server repository was rejected because the
  independently installed cross-platform client needs its own source,
  artifacts, version history, and release lifecycle.
- Enabling every capability understood by the SDK was rejected because schema
  knowledge is not proof that the deployed canonical mutation is available.
- Inferring a lease as owned because this app requested a matching port was
  rejected because restarts and concurrent devices make local history
  incomplete and non-authoritative.

The selected production constants remove unnecessary choices from the primary
journey, the separate public repository gives the universal client one durable
release identity, and runtime server evidence keeps controls honest and
least-privileged.

## Evidence and verification

Verification must prove that the Android first viewport offers the fixed
gateway connect action without legacy fields; Windows and remote macOS reach
the same OAuth contract; only verified local macOS can reveal the loopback
preview; release builds contain the exact repository slug and reject malformed
or absent configuration honestly; a newer stable release produces the
channel-appropriate prompt; absent/deferred capabilities never render active
controls; requested port bounds remain unchanged; and a lease not marked
releasable cannot be released from the client.
