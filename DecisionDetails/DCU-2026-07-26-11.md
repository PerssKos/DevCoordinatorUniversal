# DCU-2026-07-26-11 — Universal macOS builds use an explicit Intel host

## Decision

Build the macOS Release smoke app on GitHub's `macos-15-intel` hosted runner.
Keep `ARCHS = x86_64 arm64` and `ONLY_ACTIVE_ARCH = NO` in the application
Release/Profile target configurations, retain the same values as final
`FLUTTER_XCODE_*` command-line build settings, and keep Debug host-native.

The result is not accepted from configuration alone. Packaging verifies the
main executable and every embedded Mach-O with `lipo`, ad-hoc-signs the complete
bundle, archives it with resource forks and symlinks preserved, extracts it
again, and repeats the architecture, identity, callback, repository, gateway,
signature, and symlink checks. A thin or internally mixed bundle cannot become
a smoke artifact.

GitHub has announced that the hosted Intel macOS line ends after August 2027.
Before that cutoff, qualify either a supported successor build host or a
Flutter/Xcode combination that demonstrably produces the same universal bundle
on ARM. The artifact verifier is retained unchanged through that migration.

## Why

Material alternatives considered:

- Trust the Flutter/Xcode universal-release default or the Xcode project file
  without binary inspection. Rejected: GitHub's `macos-15` standard runner is
  ARM64, and the first measured build produced a thin ARM64 main executable.
- Add project-level Release architecture settings only. Rejected after a real
  CI run still produced the same thin executable.
- Add Runner Release/Profile settings plus final
  `FLUTTER_XCODE_ARCHS=x86_64 arm64` and
  `FLUTTER_XCODE_ONLY_ACTIVE_ARCH=NO` overrides on that ARM host. Rejected
  after a third real CI run showed that the settings were present in the build
  environment but the main executable remained ARM64-only.
- Publish separate Intel and Apple Silicon apps. Rejected because the requested
  desktop application should be one universal install, and separate assets
  complicate update selection, support, and rollback.
- Build two app bundles and merge their files after the fact. Rejected because
  independently produced native assets, Swift packages, frameworks, metadata,
  and signatures can diverge; a file-by-file lipo bridge would become custom
  packaging authority rather than a normal Xcode universal build.

GitHub documents `macos-15-intel` as its standard x86_64 hosted label. Using
that explicit host preserves Xcode's normal cross-compilation path while the
per-binary verifier—not the runner name—proves the universal result.

## Evidence and verification

The failing ARM-host evidence is retained in GitHub Actions runs
[30188766102](https://github.com/PerssKos/DevCoordinatorUniversal/actions/runs/30188766102),
[30189085911](https://github.com/PerssKos/DevCoordinatorUniversal/actions/runs/30189085911),
and
[30189499531](https://github.com/PerssKos/DevCoordinatorUniversal/actions/runs/30189499531).
The last run records both `FLUTTER_XCODE_*` values in the build environment
before the verifier rejects the ARM64-only main executable.

The runner identities and architectures come from GitHub's current
[hosted-runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners).
GitHub's runner-images announcement records the
[`macos-15-intel` availability window through August
2027](https://github.com/actions/runner-images/issues/13045).

The repository regression test binds dual architectures to the exact Runner
Release/Profile PBX configurations, forbids those overrides in Debug, and
binds the CI values to `macos-15-intel`. The platform smoke job remains
successful only when `verify_macos_smoke_bundle.sh` accepts the built app and
the re-extracted archive.
