# DCU-2026-07-26-06 — Remote sessions use system-browser PKCE and secure refresh rotation

## Decision

The installed app treats the configured value as an HTTPS `/api/v2` origin,
loads public gateway metadata, and rejects non-HTTPS or cross-origin OAuth
endpoints. The only public client ID is
`io.github.holyglory.devcoordinator`; the only callback is
`io.github.holyglory.devcoordinator://oauth/callback`. The explicit `oauth`
authority lets Android enforce the exact callback path in the merged
application manifest. Every interactive sign-in
creates a cryptographically random authorization state and PKCE verifier,
launches the platform browser, verifies the exact callback/state, and exchanges
the code with `code_verifier` and no client secret.

The access token and expiry stay in process memory. The current refresh token
and issuer binding are stored through `flutter_secure_storage`, replaced only
after a successful rotation response, and never written to preferences, logs,
screens, diagnostics, or update metadata. Cold launch first attempts a
non-interactive refresh. Disconnect revokes the remote device session and
clears the local record; an interrupted revocation remains a fenced cleanup
state rather than silently reconnecting with the same credential.

The application adapter maps normalized v2 DTOs into presentation models but
does not reconstruct host authority arguments or mutable-name targeting. It
retains the last strong inventory ETag, generates a new UUID idempotency key
for each user intent, safely reuses that key only when reconciling an uncertain
outcome, and reveals controls only when both capability/scope/grant and the
exact target's `allowedActions` permit them.

## Why

Material alternatives considered:

- Pasting or packaging the loopback coordinator token was rejected because it
  is host-wide and cannot be limited or revoked per user/device.
- Client Credentials and a bundled confidential-client secret were rejected
  because an APK or desktop binary cannot keep that secret.
- An embedded WebView-only login was rejected as the default because it
  weakens browser trust continuity and conflicts with installed-app OAuth
  guidance.
- Blindly accepting metadata endpoints was rejected because a compromised or
  mistyped host could direct authorization codes or refresh tokens elsewhere.
- Persisting access and refresh tokens together was rejected because the
  short-lived access token does not need durable exposure.

The selected design preserves one server-side authority while giving each
installed app a revocable, least-privilege session that can recover across app
restarts.

## Evidence and verification

Tests must cover metadata origin/scheme rejection, verifier/state uniqueness,
callback mismatch, cancel/error callbacks, code exchange, access expiry,
single-flight refresh, refresh rotation, replay/revocation responses,
secure-store failures, cold resume, offline stale inventory, logout cleanup,
minimum-client rejection, capability/scope/grant gating, immutable action
targets, ETag conflict, idempotent retry, and absence of secrets from
preferences and diagnostics. Target verification must exercise real browser
callbacks on Android, macOS, and Windows.
